The `agents` entry selects a profile for the agent; `developer: auto` means choose `fast` for mechanical, tightly specified work, `standard` for ordinary implementation, `deep` for complex investigation, or `perceptive` when environmental perception dominates. Other agents use their configured profile. Each `profiles[profile]` is an ordered, nonempty list of `{model, reasoningEffort?}` candidates. If the file, selected profile, or candidates are missing or invalid, tell the user exactly what to configure and do not silently choose a model.

Apply the first candidate using native spawn `model` and `reasoning_effort` arguments when the host supports them. Choose a fresh context and supply a self-contained brief if the host requires it for model overrides. Never put model names in the brief as a substitute. A model pinned in the custom agent TOML takes precedence; report that conflict instead of claiming the profile was applied. Try the next candidate only when a model-specific unavailability or unsupported-model error proves the agent did not start. Once an agent handle exists or execution may have begun, do not restart it on another model. Report the profile, actual model, and any fallback reason. If no candidate works, ask the user to update the configuration.

Use only parameters present in the host schema. Follow its actual schemas for spawning, follow-ups, waiting and interruption. Dispatch independent tasks together when useful, then wait for ALL dispatched tasks to return and reconcile their terminal reports before continuing substantive work or ending the turn. A returned agent id is a handle to wait on, not a finished result. Reuse an existing specialist only when the host provides a continuable handle.
